# 0.4.0 验收与实测

本报告记录隔离合成库实测，不含真实用户记忆。canonical仍为Schema5；本次没有修改真实记忆、安装目录或客户端配置。架构、API及回滚方法见[自适应检索](adaptive-retrieval.md)。

## 基线与评估方法

基线为已发布0.3.0（commit `6e9a1826efd1ea63f7e2b16381dd6cf099f5f517`）构建产物的未修改副本。审计确认：limit默认5/最多10、每个候选通道20、无继续检索、每次包含诊断。0.3已实现晚物化，因此本次不能将“全正文读取从N降到0”冒充新收益；实测新旧普通查询均为0。

[fixtures.mjs](../bench/adaptive/fixtures.mjs)在评估前冻结：240条虚构历史、120条查询、10类各12条。SHA256 `e05f6626130ae14b31bad2fe81a24d81ec31bf3e1307477ffa9d76af2478488b`。标签依据场景键和明确的相关等级，包含多相关答案、否决方案、过期/环境不符项、72条设计证据及12个无答案主题。属于明确可审计的规则标注，不是独立人工盲评；多个查询复用场景族，不能宣传为120个独立真实用户任务。标签没有根据检索结果修改。

两个版本读取相同固定数据库，使用相同BGE FP32、512维、两线程、.425/.575阈值；分别在新进程顺序测量，避免两个版本抢CPU。首次模型加载单独记录；后续延迟为warm。跨页直到has_more=false，不设置累计条目上限。@k为确定页面流的前k个去重结果；不足k个位置按0计。0.3没有续取能力，P/R@20受到最多5/7个实际返回结果的容量限制，不伪造第二页。无答案问题不进入Recall/MRR/nDCG平均，单独统计误报。详见[协议](../bench/adaptive/README.md)和[评估脚本](../scripts/benchmark-adaptive.mjs)。

## 规模与上下文 A/B

复用已有100/1,000/10,000条真实编码快照，20个单答案查询各3轮、每组60次。两版本独立进程、同样limit=5；0.3不认识mode，作为相同请求的旧检索对照。此规模集验证匹配页面的成本，不替代上面的多答案集。RSS为结束时进程RSS，包含ONNX模型和原生分配，不能当作Node堆正文量；cold指新进程首查询，不是清空OS文件缓存后的磁盘冷启动。

所有组Recall@5与MRR均为1.000，完整body读取0、元数据和Chunk读取均值5；读取量随当前页结果增长，不随全库正文增长。100→10,000的新版本全局JSON.parse观测约32.8→38.5次/页，旧版5次；新增解析主要为候选标签与查询状态，不是完整正文。新版本向量查询均值1次、返回16.9→21.4行，旧版返回40行；两者内部扫描数和距离计算数均不可观测，不能用返回行数代替。

匹配5条的输出Token约下降30%，来源仍保留。分页状态、元数据判断和多样性带来约2–4ms的常见额外成本；小库的相对百分比更明显，不能声称零性能回退。10,000条的匹配页面p95约增加4ms以内。RSS有原生分配波动，不宣称稳定降低内存；晚物化约束通过实际SQL返回和解析观测确认。

实测EXPLAIN QUERY PLAN包含 `SCAN memory_vec VIRTUAL TABLE INDEX 0:3{___}___[___*d__`、`SEARCH s USING INDEX search_scope`、`SEARCH retrieval_state.seen USING COVERING INDEX sqlite_autoindex_seen_1 (q=? AND channel=?)` 和 `SEARCH c USING INDEX chunks_memory (memory_id=?)`。授权与已发现ID过滤位于KNN的ID子查询内，未使用OFFSET；仍有精确KNN扫描、子查询及排序临时B-tree成本。

## 发现并修复的回退

第一轮严格准入：P@5 0.453、R@5 0.532，中文改写漏召回，拒绝采用。随后只放宽向量准入的版本累计Recall达到0.986，却有0.769的无关占比，也拒绝采用。加入相关性前缀保护、适用性优先、主题提示与跨情境主题族后，保留了旧版前五条质量，并显著减少扩展噪声。所有试验沿用冻结标签。

初版broad为了凑三个facet，在只有单一主题时过度探索，10,000条p95达到183.22ms；现改为低相关产出时结束当前页、显式小页请求及时形成页面，同时保留has_more/cursor，最终降至59.04ms。不是用删除可继续检索的候选换取漂亮首屏延迟。

## 可靠性与工程验证

本机完整测试45/45通过，约17秒；隔离安装器、CLI check及空库recall冒烟检查通过。[CI工作流](https://github.com/logex-linux/shared-agent-memory/actions/workflows/ci.yml)也执行完整套件及安装器/CLI检查。新增12项，加原有33项：

- 160条跨项目/global、跨月份相关证据，多页全部覆盖，无重复；旁边有1,500条无关记录，另有过期和环境不适用项。查询向量仅编码1次；普通查询完整body读取0。
- 单条相关记忆只返回1条；auto根据多情境偏好分布扩大检索；显式大limit通过Schema但受单页配置保护。
- 四进程同时继续同一cursor，重启后重放相同ID和Chunk选择；四进程独立按窄权限取完58条，无越权。
- 写入进程与分页读取并发；新增、更新和遗忘后拒绝旧cursor，包括旧页重放。更新/遗忘后新查询不返回旧revision。
- 过期状态、配置权限变化、项目过滤、失效索引、未知cursor、TTL、页选项冲突、管理员收紧预算均明确处理。
- 查询缓存写入中SIGKILL后可恢复；原有400条四进程写入、双写Revision冲突、10个SIGKILL故障点和Schema4→5迁移/回滚测试继续通过。
- 模型损坏/编码失败明确lexical_degraded；词法分页仍能取完57条合成证据，未伪装正常语义检索。
- 官方MCP SDK实际取完61条短证据；默认不含diagnostics，来源和核验状态保留，连接只暴露recall。
- 超长来源无法容纳时返回blocked_ids和同页cursor；增大预算可继续。debug与正常重放选择相同内容，不挤占内容Token预算。

并发可靠性使用真实多个OS进程、确定性测试编码器，验证的是锁、权限和一致性；真实BGE延迟使用单进程基准。尚未提供四个真实ONNX模型同时运行的延迟承诺，也没有用假编码器结果代替真实模型质量。

## 剩余边界

精确KNN与权限/完整性子查询仍随索引规模增长；缓存反连接避免深OFFSET，但不会变成ANN。SQLite中的facet窗口、缓存清理及精确查询仍有扫描成本。原生同步SQL和锁等待不可被JS计时器抢占，time_budget只是协作式保护。缓存写事务序列化页面创建，超过当前四进程规模需要继续压测；每个MCP子进程各自加载模型也是主要RSS成本。

时间多样性使用首来源checked_at月份作为可用代理，不能当作事件真正发生时间。标签质量会影响主题分布；无标签、不一致标签、多语言和含糊查询仍可能漏召回或产生噪声。已生成页面固定顺序和Chunk选择，但后续通道可能发现分数更高的候选，不宣称整个跨页流等价于一次无预算全局排序。可用更明确的主题/项目/context或多次改写补充证据。

下一步应在用户另行授权的真实匿名评估集上做独立标注，专门改善代码登记/否决方案与实际修复的区分，并量化更多并发真实模型的成本；不通过自动改写、删除或合并已有记忆来提高分数。
